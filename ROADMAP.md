# Roadmap: Training Plan

Этот файл служит «внешней памятью» для управления контекстом AI-агента (элементы GSD). Перед началом работы над новой фазой рекомендуется перечитать этот файл и `AGENTS.md`, чтобы «сбросить» контекст Cursor.

## Текущий статус
- **Функционал:** ~20%
- **Процесс:** Harness внедрён (`AGENTS.md`), SDD и TDD применяются точечно.
- **Фокус:** Фаза A — создание и управление планом тренера.

## Фаза A: CRUD для плана тренера (Текущая)

**Цель:** Дать тренеру возможность создавать, редактировать и удалять тренировочные дни, а спортсмену — видеть их.

### A1. Сохранение плана дня тренером
- **Спецификации:** `specs/001-save-builder-day.md` (клиент), `specs/003-day-plan-mock.md` (мок).
- **FSD** (`specs/refactor-001-roadmap-a1-fsd.md`):
  - `widgets/builder-day/ui/BuilderDay.tsx` — пункт «Сохранить». Отдельной кнопки нет. Доступен, когда дата в режиме редактирования и в `activeKeys` есть хотя бы один ключ. Пока запрос идёт, подпись «Сохранение…» и пункт заблокирован.
  - `features/save-builder-day/model/useSaveBuilderDay.ts` — принимает `{ date, athleteId, workoutName, plan }` и вызывает мутацию. Ошибка сети и сервера — `alert()` с пометкой `// TODO: replace with Toast`. Наружу: сохранение и `isLoading`. Аргументы собирает виджет: фича соседние фичи не импортирует.
  - `entities/day-plan/api/dayPlanApi.ts` — `saveBuilderDay` через `injectEndpoints` того же `dayPlanApi`, `invalidatesTags: ["DayPlan"]`. Сущность `builder-day` и второй `createApi` не заводятся.
  - `entities/day-plan/model/types.ts` — `SaveBuilderDayBody`: `{ date, athleteId, workoutName, plan }`. Ответ мутации — `DayData`: `{ date, athleteId, workoutName, plan }`.
  - `features/select-athlete/` — слайс выбранного спортсмена. Редьюсер подключается в `src/App/store/index.ts`. Модуль `@/entities/day-plan` там уже импортирован, отдельный импорт для мутации не нужен.
- **Мок (`server/`, типы из `src/` не импортирует):**
  - `server/app.ts` — `express.json()`, память `Map` по паре `athleteId` + `date`, `GET /api/dayPlan`, `POST /api/saveBuilderDay`.
  - `server/index.ts` — слушает порт `3001`.
  - `POST` и `GET` отвечают `{ date, athleteId, workoutName, plan }`. `plan` в ответе равен строковым полям тела `plan`. Поле `sections` в теле не читается. Повторный `POST` той же пары заменяет `plan` и `workoutName` и не трогает другого спортсмена. Пара без сохранения — `{ date, athleteId, workoutName: "", plan: {} }`. Нет `date` или пустой `athleteId` — `400`. `workoutName` хранится отдельно от `plan`.
- **Тесты (TDD):**
  - `features/save-builder-day/model/useSaveBuilderDay.test.tsx` — успех инвалидирует тег `DayPlan`; ошибка вызывает `alert`.
  - `server/dayPlan.test.ts` — `POST` затем `GET`, замена плана, пустая дата, `POST` без `athleteId`.
- **Критерий готовности:** Тренер сохраняет блоки дня. Мок помнит их по паре спортсмен + дата. Инвалидация `DayPlan` заставляет `useDayPlanQuery` перечитать `GET /api/dayPlan`, и спортсмен видит эти блоки в `DayView`.
- **Несохранённая смена даты или спортсмена** (`specs/delta-003-unsaved-date-change.md`): календарь и выбор спортсмена на экране тренера не применяют переход, пока в черновике есть несохранённые правки. `BuilderDay` показывает одно окно «Сохранить» / «Отменить изменения». Календарь спортсмена и экран без конструктора меняют выбор сразу.

### A2. Копирование плана в другую дату
- **Спецификация:** `specs/002-copy-buider-day.md`.
- **FSD:**
  - `widgets/builder-day/ui/BuilderDay.tsx` — пункты «Копировать» и «Вставить». Отдельных кнопок нет. Буфер — `DayDraft` в состоянии виджета, один на сессию конструктора. Смена `selectCurrentDate` его не очищает.
  - «Копировать» доступен, когда черновик даты уже есть: его заполнил `GET` или тренер уже менял дату. Пока запрос даты без черновика не завершился, пункт заблокирован. В буфер кладётся копия `workoutName`, `activeKeys` и `texts`.
  - «Вставить» заблокирован, пока буфер пуст. Вставка заменяет черновик выбранной даты целиком и включает режим редактирования. `POST` не шлётся. Новая фича, новый эндпоинт и второй `createApi` не заводятся.
  - Запись вставленного плана — пункт «Сохранить» из A1. Мок A1 не меняется.
- **Тесты (TDD):** `widgets/builder-day/ui/BuilderDay.test.tsx` — копирование названия и блоков, включая пустую строку; блокировка копирования до готовности черновика; замена черновика другой даты без слияния; исходная дата и буфер после правки источника не меняются; вставка не вызывает сохранение, следующее «Сохранить» уходит с датой новой карточки; ответ `GET` после вставки черновик не затирает.
- **Критерий готовности:** Тренер копирует день и вставляет его в другую дату. Спортсмен видит вставленные блоки в `DayView` только после «Сохранить» на эту дату.
- Правка уже сохранённого дня в отдельную спеку не выносится. Её закрывают Spec 001 и `specs/delta-002-initialstate-builder-day.md`: `BuilderDay` заполняет черновик из `GET /api/dayPlan`, повторное «Сохранить» заменяет запись даты через `POST`. Эндпоинт `updateDayPlan` (`PUT`/`PATCH`) не заводится.

### A3. Удаление упражнения из дня
- **Спецификация:** `specs/010-remove-exercise.md` (создать). Номера 003–005 заняты моком, умным действием и его клиентом.
- **FSD:**
  - `features/remove-exercise/` — кнопка удаления и хук.
  - `widgets/builder-day/` — интеграция кнопки в список упражнений.
- **Тесты:** Проверка, что селектор `selectDayPlanSections` возвращает обновленный список после удаления.

### A4. Индивидуальный план спортсмена
- **Спецификация:** `specs/delta-004-day-plan-by-athlete.md`. Это правка Spec 001, Spec 002 и Spec 003, не отдельная фича.
- **Контракт:** `GET` и хранилище мока принимают пару `athleteId` + `date`. `POST` одного спортсмена не заменяет план другого на ту же дату. Черновик `BuilderDay` тоже хранится по этой паре.
- **Код:** `GET` и хранилище идут по паре. `useDayPlanQuery(athleteId)` вызывают `BuilderDay` и `DayView`.
- **Вне объёма:** свой id спортсмена при входе под ролью `athlete`. До фазы C `DayView` показывает спортсмена, выбранного тренером в сторе.

### A5. Умные действия дня через LLM
- **Спецификации:** `specs/004-llm-day-actions.md` (сервер), `specs/005-smart-day-action.md` (меню «…» в BuilderDay). Поле блоков в сохранении и в JSON модели одно: `plan` (`specs/delta-005-unify-plan-field.md`). Модель Groq актуализирована в `specs/delta-006-groq-model.md`.
- **Сервер (`server/`, типы из `src/` не импортирует):**
  - `server/app.ts` держит `Map`, ищет пару и вызывает `server/smartAction.ts`. Этот файл не импортирует `app.ts`.
  - `POST /api/smartAction` принимает `{ date, athleteId, action }`. `workoutName` и `plan` читаются из `Map` той же пары. Ответ — SSE: строки `data: {"text":...}`, в конце `data: [DONE]`.
  - Нет поля, пустая строка или не строка — `400`. Пары нет в `Map` — `404`. Ошибка LLM до заголовков — `500`. После начала потока ошибка уходит как `data: {"error":...}` без `[DONE]`.
  - Модель Groq `openai/gpt-oss-120b`, `temperature: 0.3`. `Map` на время запроса не меняется. Запись результата — `POST /api/saveBuilderDay` с тем же полем `plan`.
- **Тесты (TDD):** `server/smartAction.test.ts` — поток кусков и `[DONE]`, промпт из записи `Map`, `400` и `404`, `500` до потока, `error` после первого куска, `GET` пары после потока не меняется.
- **Клиент** (`specs/005-smart-day-action.md`):
  - `widgets/builder-day/ui/BuilderDay.tsx` — в том же меню пункты «Сделай этот день легче» и «Замени основную работу на интервалы». Пока черновик не готов или есть несохранённые правки, пункты заблокированы. Каждый кусок дописывает уже начатые поля дня, например «Основная работа». Сырой JSON на экран не выводится.
  - `features/smart-day-action/` — хук запуска, две подписи и разбор JSON после `[DONE]`, включая снятие ограды markdown. Сохранение хук не вызывает. Соседние фичи не импортирует.
  - `entities/day-plan/api/dayPlanApi.ts` — мутация `smartAction` через тот же `injectEndpoints`. Куски SSE читает её `queryFn`. Тег `DayPlan` инвалидирует только последующий `saveBuilderDay`.
  - После `[DONE]` виджет шлёт `POST /api/saveBuilderDay` с парой исходного нажатия и с `workoutName` и `plan` модели. Успех заменяет черновик известных блоков.
- **Критерий готовности:** Действие тренера переписывает только сохранённый день и приходит потоком. Неделя не генерируется. В мок результат попадает только через «Сохранить» после `[DONE]`.

## Фаза D: Качество и DevOps (опционально)

**Цель:** Подготовить проект к «продакшену».

- **D1. CI/CD:** GitHub Actions для `typecheck`, `test:run`, `build` на каждый пуш в `dev`.
- **D2. E2E-тесты:** Playwright для сценария «тренер создает день → спортсмен видит его».
- **D3. Деплой:** Vercel (frontend) + Render (mock server) или Supabase (замена мока).
- **D4. Мониторинг:** Sentry для отслеживания ошибок в production.

## Как работать с этим файлом

1. **Перед началом сессии в Cursor:** Откройте `ROADMAP.md` и `AGENTS.md`, чтобы «прогрузить» контекст.
2. **При старте новой задачи:** Создайте спецификацию в `specs/` (SDD), затем попросите Cursor составить план (Plan Mode).
3. **После завершения задачи:** Отметьте ее как выполненную (`[x]`) и обновите `README.md` в разделе «Roadmap», если нужно.
4. **При переходе к новой фазе:** Убедитесь, что все задачи предыдущей фазы закрыты или осознанно перенесены.
