# Spec 004: Умные действия дня через LLM

Связана со Spec 001 и Spec 003. Эта спека — сервер: новый `POST /api/smartAction`. Клиент меню «…» сюда не входит. Эндпоинт читает запись пары из `Map` Spec 003 и не записывает в него. Сохранение результата остаётся `POST /api/saveBuilderDay`.

## User Story
Как тренер, я хочу нажать «…» на карточке дня и выбрать действие («Сделай этот день легче», «Замени основную работу на интервалы»), чтобы LLM переписала только этот день, а я увидел результат в реальном времени, не перегенерируя всю неделю.

Сервер принимает дату, спортсмена и текст действия. Фразы действий — это `action`, который пришлёт клиент. Свой список действий сервер не хранит. `workoutName` и `plan` берутся из хранилища, а не из тела запроса.

## Acceptance Criteria
1. `POST /api/smartAction` с JSON-телом `{ date, athleteId, action }` и существующей записью пары отвечает `200`. Заголовки: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. `express.json()` разбирает тело до потока.
2. Каждый непустой кусок текста модели уходит одной строкой `data: {"text":"<кусок>"}\n\n`. Куски идут в том порядке, в каком их отдаёт модель. Перевод строки внутри куска экранирован в JSON, поэтому событие остаётся одной строкой. Пустой кусок не отправляется.
3. После последнего куска сервер пишет `data: [DONE]\n\n` и закрывает соединение. `[DONE]` — это буква окончания потока, не JSON и не поле `text`. Сервер не собирает ответ модели, не снимает markdown и не проверяет JSON.
4. В модель уходят `workoutName` и `plan` записи этой пары и строка `action`. Другая дата, другой спортсмен и неделя в запрос модели не попадают. Системный промпт содержит фразу «Верни только JSON, без markdown», требует объект `{ workoutName: string, plan: Record<string, string> }` без пояснений, просит сохранить стиль и терминологию исходного плана и оставить без изменений поля, которых действие не касается. `plan` — то же поле, что в `DayData` и в `Map`. `workoutName` в `plan` не входит. Ключи блоков те же, что у сохранения: `warmUp`, `main`, `intervals`, `stretch`, `strength`, `coolDown`, `note`. Пустая строка блока допустима. Уже сохранённый неизвестный ключ остаётся, как его хранит Spec 003.
5. Запрос не меняет `Map`. `GET /api/dayPlan` той же пары после потока отдаёт прежнюю запись. Запись ответа делает клиент отдельным `POST /api/saveBuilderDay` после `[DONE]`: `date` и `athleteId` исходного запроса, `workoutName` и `plan` из JSON модели. Поле остаётся `plan`. `POST /api/smartAction` в `Map` не пишет.
6. Проверка идёт в том же порядке, что `GET /api/dayPlan` и `POST /api/saveBuilderDay`: сначала `date`, затем `athleteId`, затем `action`. Нет поля, значение не строка или строка пустая после обрезки пробелов — `400`, `Content-Type: application/json` и поток не открывается. Для `date` сообщение `{ message: "Параметр date обязателен" }`. Для `athleteId` — `{ message: "Параметр athleteId обязателен" }`. Для `action` — `{ message: "Параметр action обязателен" }`. Ключ хранилища строится из уже обрезанных строк, как в Spec 003: `athleteId + "\0" + date`. Хранилище не меняется.
7. Пары нет в `Map` — `404`, `Content-Type: application/json` и `{ message: "План на эту дату не найден" }`. Поток не открывается. В отличие от `GET`, отсутствие ключа не подменяется телом `{ date, athleteId, workoutName: "", plan: {} }`. Сохранённая запись с пустым `plan` в модель уходит.
8. Ошибка LLM до отправки заголовков — `500`, `Content-Type: application/json` и `{ message: "..." }`. Нет `GROQ_API_KEY` и нет подставной модели — `{ message: "LLM не настроен" }`. Ответ провайдера не `200` или обрыв до первого байта потока — `{ message: "LLM недоступна" }`. Подставная модель ключ не требует. Успешный ответ этим JSON не является: это не `DayData`.
9. Ошибка LLM после начала потока — одна строка `data: {"error":"LLM недоступна"}\n\n`, затем соединение закрывается. `data: [DONE]` после ошибки нет. Уже отправленные куски `text` остаются. HTTP-статус при этом уже `200`.
10. Закрытие соединения клиентом прерывает чтение модели. В хранилище по-прежнему ничего не пишется.
11. Провайдер — Groq, `POST https://api.groq.com/openai/v1/chat/completions`, `stream: true`. Модель `llama-3.3-70b-versatile`, `temperature: 0.3`. Ключ уходит заголовком `Authorization: Bearer <GROQ_API_KEY>`. Из чанков Groq читается только текст `choices[0].delta.content`.

## Контракт

Сервер повторяет контракт своими типами и из `src/` ничего не импортирует. Запись в `Map` та же, что в Spec 003: ключ `athleteId + "\0" + date`, значение `{ workoutName, plan }`.

```ts
type SmartActionRequestBody = {
  date: string;
  athleteId: string;
  action: string;
};
```

Пример. В `Map` уже лежит план Иванова на `2026-11-04`: название «Лёгкий бег», разминка и основная работа.

```http
POST /api/smartAction
Content-Type: application/json

{
  "date": "2026-11-04",
  "athleteId": "ivanov",
  "action": "Сделай этот день легче"
}
```

```text
data: {"text":"{"}

data: {"text":"\"workoutName\":\"Восстановительный бег\""}

data: [DONE]
```

Системный промпт:

```text
Ты правишь один тренировочный день. Верни только JSON, без markdown и без пояснений.
Форма ответа: {"workoutName": string, "plan": Record<string, string>}.
plan — блоки дня. Ключи: warmUp, main, intervals, stretch, strength, coolDown, note. workoutName в plan не входит. Пустая строка блока допустима.
Сохраняй стиль и терминологию исходного плана.
Поля плана, которых действие не касается, оставь без изменений, включая уже сохранённый неизвестный ключ.
Не добавляй date, athleteId, другие даты и неделю.
```

Сообщение пользователя:

```text
Текущий день:
{"workoutName":"Лёгкий бег","plan":{"warmUp":"10 минут легко","main":"40 минут ровно"}}

Действие тренера:
Сделай этот день легче
```

Тело запроса к Groq содержит эти два сообщения, `model: "llama-3.3-70b-versatile"` и `temperature: 0.3`.

Поле `plan` в этом JSON совпадает с `DayData.plan`, со значением `Map` и с телом `POST /api/saveBuilderDay` (Delta 005). Клиент после `[DONE]` отправляет его под тем же именем. `date` и `athleteId` в ответ модели не входят: в моке они лежат в ключе, а не в записи.

## Размещение
Код действия живёт в отдельном файле. `Map` остаётся в `server/app.ts` и в новый модуль не переезжает.

- `server/app.ts` — маршрут `POST /api/smartAction`. Обрезает `date` и `athleteId` теми же правилами, что `GET` и `POST /api/saveBuilderDay`, ищет пару в своём `Map` и вызывает функцию из `server/smartAction.ts`. В функцию уходят обрезанные `date` и `athleteId`, поле `action` и запись `{ workoutName, plan }`. Нет `date` или `athleteId` — `400` отсюда. Пары нет — `404` отсюда, до Groq. `GET /api/dayPlan` и `POST /api/saveBuilderDay` не меняются. `Map` не экспортируется.
- `server/smartAction.ts` — проверка `action`, сбор промпта, запись SSE и запрос к Groq. Файл не импортирует `app.ts` и к `Map` не обращается. Запись приходит аргументом.
- Тест подменяет источник кусков через функцию из `server/smartAction.ts` и после себя возвращает источник по умолчанию. `400` по `date` и `athleteId` и `404` проверяются через маршрут приложения.

## Out of Scope
- Пункт «…», подписи действий и показ потока в `BuilderDay`.
- Сборка текста на клиенте, снятие ограды ` ```json ` и `JSON.parse`. Это сделает клиент следующей спеки. Spec 003 по-прежнему только хранит план и ограду не разбирает.
- Запись ответа модели в `Map`. Пока тренер не нажал «Сохранить», `GET /api/dayPlan` отдаёт прежнюю запись.
- Проверка на сервере, что незатронутые поля плана совпали с исходными. Это требование к промпту, не к разбору ответа.
- Неделя и план другого спортсмена.
- Второй `createApi`, прямой `fetch` из `src/` и тип эндпоинта в `entities/day-plan`.
- Учётная запись, лимит частоты и оплата токенов.
- Проверка, что `athleteId` есть в `mockAthletes`.
